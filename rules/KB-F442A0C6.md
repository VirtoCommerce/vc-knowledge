BL-LOY-015: A subsystem that settles many entities per event MUST expose per-entity attribution of the settlement `[P0-revenue]`

- **Rule:** Where a single business event (an order insert) settles MULTIPLE independent entities in one pass — several loyalty missions advancing and granting from one order — each resulting ledger entry MUST be attributable, through a reachable API, to the specific entity that caused it. A points-ledger row MUST let a caller answer *"which mission granted this?"*, and a progress record MUST let a caller answer *"did this order contribute to this mission?"*. An aggregate — a balance total, a history row count, a sum — is NOT attribution: it is moved by every entity that settled in the same event, so it can neither confirm nor refute any single entity's contribution.
- **Verify:** Introspect the loyalty GraphQL surface and read a settled ledger entry: the entry (or a sibling query reachable by the same caller) MUST carry the id of the granting mission alongside the order reference. Then place one order that satisfies two or more missions and confirm each grant is separately identifiable. Not satisfied by an entry that carries only an order reference, because one order legitimately produces several entries.
- **Violation signal:** The ledger row exposes only an order reference (`type` / `orderId` / `orderNumber`) and no entity id; a single order yields multiple grant rows that cannot be told apart except by amount; a test or a customer asking "which mission paid these points?" has no query that answers it. Downstream symptom: every assertion about one entity's contribution degrades to a total, and any such assertion silently measures co-settling entities as well.
- **Agents:** qa-backend-expert
- **Docs:** StorefrontUserGuide → *Points History*: "This section shows the number of points earned and redeemed **for each order**, as well as the total balance of points remaining." PlatformDeveloperGuide → xAPI *Loyalty* overview documents the entire storefront loyalty surface as `loyaltyBalance` + `loyaltyPointsHistory`, and describes `LoyaltyOperationLogObject` as "the object associated with a loyalty program operation log entry, such as an order". Both state a per-causing-object attribution model; the mission path satisfies neither. **The prior `Docs: N/A` claim was wrong** — the ledger surface IS documented even though missions themselves are not (re-checked 2026-09-14).
- **Source:** `VirtoCommerce/vc-module-loyalty` @ `1be73b4` — `LoyaltyMissionTransaction` carries `MissionId`, `ObjectId`, `UserId` behind `IX_LoyaltyMissionTransaction_MissionId_ObjectId_UserId` and is the record the accrual dedup reads (`LoyaltyMissionLogicService.cs:311`, `:488-497`), but no query, type or field exposes it. Live introspection of the deployed schema (2026-08-28, vcst-qa): the entire loyalty surface is `loyaltyBalance(userId, orderId)` / `loyaltyPointsHistory(...)` / `loyaltyMissionProgress(...)`; `LoyaltyOperationLogObject` exposes only `type`, `orderId`, `orderNumber`; the only `missionId` in the schema is `LoyaltyUserMission.missionId`, which is the progress record, not the grant. Measured consequence, run `REG-2026-08-28-1154`: one order granted `+250 / +200 / +100 / +0` across four missions, so the account's balance moved by 1058 while the mission under test contributed 508.
- **Source (read-side anchor, re-read 2026-09-14 against the deployed build):** `VirtoCommerce/vc-module-loyalty` — `ExperienceApi/Extensions/DataLoaderContextAccessorExtensions.cs` → `LoadLoyaltyObject()` now carries a third switch arm, `nameof(LoyaltyMissionProgress) => new LoyaltyOperationLogObject { Type = "Mission" }`. It sets the discriminator ONLY: `LoyaltyOperationLogObject` is `{ Type, OrderId, OrderNumber }` (`Core/Models/LoyaltyOperationLogObject.cs`), so a mission row returns `{type: "Mission", orderId: null, orderNumber: null}` and the type has no field that could carry a mission id. `Schemas/LoyaltyOperationLogType.cs` projects `id`, `operationType`, `amount`, `createdDate`, `object` — no `userId`, no `sourceId`, no `sourceType`, although `Core/Models/LoyaltyBalanceOperationLog` persists all four.
- **THE DISCRIMINATOR MOVED — do not assert `object == null` on a mission row.** Until this arm shipped, a mission grant projected `object: null`, and cases were written against that. On the deployed build the row projects `{type: "Mission"}`, so an `object == null` assertion now FAILS on a build where the attribution gap is unchanged. The correct discriminator is `object.orderId == null && object.orderNumber == null` on an `Earned` row whose `type` is `"Mission"` — a grant that names no causing entity. **Corpus swept 2026-09-14 — exposure is currently ZERO, and this note is forward-looking rather than a live defect:** the only case carrying the old assertion (`075d` MSN-019) is `Deprecated` and so runs nowhere (`EX-201`), and its live successor (`075d` MSN-033) already asserts `object.type = Mission`. One stale prose cross-reference remains in MSN-033's `Cross_Layer_Checks`, which names MSN-019 as "the direct precedent for the `object===null` shape" — a comment, not an executable assertion. Measured live 2026-09-14: one page of `loyaltyPointsHistory` returned nine mission rows in which four distinct amounts EACH APPEARED TWICE — two distinct missions, same amount, same date, identical in every projected field. That pair is the violation in its purest form: the maximum discrimination the storefront permits is the amount, and the amount is not unique.
- **BOTH clauses fail for the storefront caller; the SECOND fails for every caller.** Clause 1 ("which mission granted this?") is answerable by an admin-scoped caller — the REST ledger row carries `sourceType: "LoyaltyMission"` plus `sourceId` (the mission id) and `objectId` (the progress id). Clause 2 ("did this order contribute to this mission?") is answerable by NOBODY: the record that holds it, `LoyaltyMissionTransaction (MissionId, ObjectId=orderId, UserId, ContributionValue)`, has no REST controller and no GraphQL type (probed 2026-09-14: the expected search routes return 404), and `Schemas/LoyaltyUserMissionType.cs` exposes progress aggregates only — `currentValue`, `percentage`, `items` — with no contributing-order list. So clause 2 cannot be closed by a resolver arm; it needs a new read surface. Cost therefore splits: clause 1 is one resolver arm plus two fields; clause 2 is a new endpoint.
- **Amended:** 2026-09-14 (auto-applied, triangulated — BL-AUDIT-2026-09-14) — Rule and Status unchanged; the Docs axis was wrongly recorded as N/A, the read-side anchor had moved, and the `object == null` discriminator is now a corpus hazard.
- **NARROWED 2026-09-08 — the gap is READ-SIDE, not write-side, and it is one `switch` arm wide.** The earlier reading that "mission grants are attributable to nothing" and that "the maximum discrimination the API permits is the amount" was taken against the **GraphQL surface only**, and is **not true of the record**. The stored ledger row carries full attribution: a Platform REST read of the same entries returns `objectType: "LoyaltyMissionProgress"` **plus** an `objectId` (the mission-progress id, one hop from the mission) on every mission-granted row, while order-driven rows carry `objectType: "CustomerOrder"`. The two layers disagree on the *same* entry — REST `{objectType: "LoyaltyMissionProgress", objectId: <id>}` vs xAPI `{object: null}` — because the xAPI resolver's `objectType switch` handles only `CustomerOrder` and `ApplicationUser` and drops everything else to a `null`-returning default arm. **Consequences:** (a) the invariant is closable with a resolver arm rather than a schema redesign, so its cost estimate drops sharply; (b) an admin-scoped caller CAN answer "which mission granted this?" today, so the attribution exists and is merely unreachable for the storefront caller the Rule is written about; (c) for authoring against the storefront xAPI nothing changes — `object` is still `null` on a mission row, and amount + count remain the only discriminators there.
- **Status:** VIOLATED for the caller the Rule names — a storefront/xAPI caller still cannot attribute a mission grant. **Not** violated at the persistence layer: the record carries the attribution and only the read projection loses it. Stated as an invariant the subsystem must satisfy, not as a description of what it does.
