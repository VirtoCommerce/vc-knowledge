The configuration a buyer assembled is not carried onto the order in the shape it had in the cart. CartConfigurationItemType has eight fields -- id, name, type, customText, files, productId, quantity and sectionId. OrderConfigurationItemType has five: id, name, type, customText and files. productId, quantity and sectionId are all dropped. So for a configuration section whose type is 'Product', the order records the chosen option's NAME and nothing that identifies the product it was or how many were taken, and it does not record which section the choice answered. Anything reconciling a configured order back to catalog products has only a display string to match on. This is read off the deployment's own schema rather than from a placed order: read the same two type tables on any deployment and a diff either confirms it or retires it.

**Disputed.** Checked against a real placed order (the entry says it was read off the schema, and that is where it goes wrong). The SCHEMA DIFF it reports is right and the conclusion drawn from it is not. The stored order keeps the product and the quantity: GET /api/order/customerOrders/{id} returned, per Product-type configuration item, productId, sku, quantity, imageUrl, catalogId and categoryId alongside name and type -- so the order does identify the catalog product that was chosen and how many were taken. Comparing the two stored shapes in the modules' own swagger, CartConfigurationItem carries 16 fields and OrderConfigurationItem 15, and the ONLY field the crossing loses is sectionId. What the entry actually describes is the storefront GraphQL projection of an order: OrderConfigurationItemType exposes 5 fields and refuses productId, quantity, sectionId, sku, catalogId, categoryId and imageUrl by validation error. So the loss is in one read surface, not in the record. — observed on `vcptcore_stable`.
