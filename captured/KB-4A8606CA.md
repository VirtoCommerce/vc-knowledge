You may not be able to. Walking an un-accepted invitation through the controls a maintainer actually has - invite, Edit role, Block user, Unblock user, Delete - left the provisioned security account in a state where every id-keyed route in the platform stops finding it while the name-keyed ones still do. Observed on one account after that sequence: GET /api/platform/security/users/{userName} and /users/email/{email} both return it in full, but GET /api/platform/security/users/id/{id} returns null for the id those responses themselves carry, POST /api/platform/security/users/search returns totalCount 0 for it by keyword, by memberId and even unfiltered, the Admin Users grid therefore cannot show it, the Admin contact blade's Accounts widget counts 0, and DELETE /api/platform/security/users?names=... fails with ConcurrencyFailure 'object has been modified' on every retry, in either letter case, whether or not the contact it points at still exists. The same three routes work on control accounts in the same store, so this is one record and not a broken endpoint. The consequence is that the standard remedy - 'delete the account under Security > Users' - has no handle to grab, the address stays permanently taken so the person can never be invited again, and the record can only be reached by already knowing the exact user name. Before you walk an invitation backwards, write the invited address down; and treat an invitation to a wrong address as something to escalate to whoever can reach the database, not as something the UI can undo. I did not isolate which step in the sequence causes it.

**Anchor corrected.** `GET /api/platform/security/users/id` → `GET /api/platform/security/users/id/{id}` — the route takes the id as a path parameter and the anchor dropped it, so it resolved to nothing.
