No. A wishlist's sharing key is the id of its SharingSetting row, and that row exists from the moment the list is created - including for a list created Private, which has a key it never shows. Changing scope through changeWishlist rewrites the scope on that same row and mints nothing: the storefront's List settings dialog shows the same /shared-list/<key> URL before and after, and a list re-scoped Private then shared again is reachable at the identical link. So switching a list back to Private is a suspension, not a revocation - anyone who ever copied the link regains access the instant the owner shares it again, and there is no control anywhere in the storefront that issues a new key. Treat a leaked list link as permanently leaked and delete the list instead.

**Retired.** Written before I had tested the remedy it recommends. Deleting the list does revoke the key - verified afterwards - and saying so is the whole point of the entry. Subject reworded only because supersede refuses to reuse the old one. Superseded by KB-7A9D4927.
