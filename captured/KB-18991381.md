The order-level coupons list is a STOREFRONT-ONLY field. The xAPI type a shopper's own client reads, CustomerOrderType, carries coupons among its fields; the REST CustomerOrder does not have the property at all - the deployment's own swagger (/docs/VirtoCommerce.Orders/swagger.json) declares 80 properties on CustomerOrder and none of them is coupons, and the live payload matches, on an API that demonstrably serializes nulls. So an operator working from the Orders API or the Admin blade has no order-level coupon field to read and no empty one to notice; the only trace is discounts[].coupon, one per discount row, which is null for an automatic promotion and is the single place a code can appear. Two practical consequences: a report that joins orders to coupons must go through the discount rows, not the order header, and an agent that introspects the GraphQL schema to decide what the ORDER record holds will be wrong about the record - the two contracts over one row are not the same shape, and the customer-facing one is the richer of the two.
