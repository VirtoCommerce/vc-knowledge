A product's configurability is NOT a field on the product. GET /api/catalog/products/{id} returns the full CatalogProduct record -- 60+ fields including mainProductId, variations and productType -- and carries no isConfigurable and no configuration at all, so reading products can never tell you. The configuration is a separate entity keyed by productId, and POST /api/catalog/products/configurations/search with an empty criteria body is the authority: its totalCount is the number of configurable products on the whole deployment. Note also that productType is Physical/Digital/null -- 'Configurable' is not one of its values, so filtering products by type finds nothing either. The storefront GraphQL Product type does expose a computed isConfigurable, but only for products the search index holds, so it answers a narrower question than the REST route does. A catalog can hold the configuration OPTION products (the parts a configuration is assembled from) and categories named for configurables while having no configurable product at all -- the options are ordinary products and look like any other.

**Disputed.** One clause only, and I am the one who confirmed this entry earlier today -- which is how the clause survived. The claim that POST /api/catalog/products/configurations/search with an empty criteria body gives 'the number of configurable products on the whole deployment' is not right: the empty body counts configurations regardless of isActive. I confirmed it when the store held zero configurations, where both readings give 0 and nothing can tell them apart. After creating one and then deactivating it, the empty body returns totalCount 1 while {isActive:true} returns 0 and the product reads isConfigurable false. Since there is no delete route (@kb(KB-7AB0B13E)), deactivated rows are permanent, so the empty-body count drifts upward from the number of genuinely configurable products and never comes back. Everything else in this entry held exactly: configurability really is a separate entity keyed by productId, GET /api/catalog/products/{id} really carries nothing about it, productType really has no 'Configurable' value, and the option products really do look like ordinary products. Use {isActive:true} for the count -- see @kb(KB-8A82CF4D). — observed on `vcptcore_stable`.
