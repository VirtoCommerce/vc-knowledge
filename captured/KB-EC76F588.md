PaymentMethodCode is not a property of PaymentIn. It is absent because it does not exist, not because it is null - and that is testable on the payload rather than assumed: round two's three arms established that this API serializes nulls, with purpose, incomingDate, processPaymentResult and taxType all present as null in the same inPayments[0] object, so a declared-but-empty property would have shown as paymentMethodCode: null. What carries the gateway code is PaymentIn.GatewayCode (Model/PaymentIn.cs l. 22); the resolved definition is the PaymentMethod object (l. 26), whose code reads the same value, because CustomerOrderBuilder copies GatewayCode from the cart's PaymentGatewayCode. The naming is NOT symmetric with its sibling model: Shipment carries ShipmentMethodCode (l. 27) and ShipmentMethodOption (l. 32) alongside its ShippingMethod object (l. 37). So shipmentMethodCode exists and paymentMethodCode does not, and expecting the second because the first is there is the trap. No surface in the stack spells it paymentMethodCode.
