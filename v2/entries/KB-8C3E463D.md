Both, and the offset is not the browser's. Admin formats an order timestamp in the timezone stored on the SIGNED-IN OPERATOR'S PROFILE: GET /api/platform/profiles/currentuser carries VirtoCommerce.Platform.UI.TimeZone alongside UI.Language and UI.RegionalFormat, and the order blade and the orders grid both render createdDate through it, printing no offset. Here the profile said America/New_York while the machine running the browser was Asia/Yerevan (UTC+4), so an order created at 08:17:18Z displayed as 4:17:18 AM - eight hours from the viewer's own wall clock and four from UTC. The consequence is that two operators looking at one order see two different clock times according to a per-user setting neither of them is looking at, and neither reading matches the API. Do not reconcile a screen time with a payload time by assuming the reader's timezone; open the profile first. Two more traps on the same blade. The indexation widget at the bottom prints the SAME KIND of value in raw UTC instead (Indexed reads one second after the record's modifiedDate Z-value), so one blade shows two clocks four hours apart and labels neither. And a blade reached by a cold deep link, before the profile has loaded, falls back to the BROWSER's timezone and a ja-JP date pattern, so the same order can print two different creation times in the same session depending on how the blade was opened.

**Anchor corrected.** `CustomerOrder.createdDate` → `GET /api/order/customerOrders/{id}` — The REST DTO field name is not a coordinate this base projects; the route that serves the UTC value the claim compares against is.
