Everywhere. A promotion's store axis is a LIST (storeIds, rendered on the blade as 'Stores' with the caption 'Stores where this promotion applies'), and an EMPTY list means every store, not no store - established the hard way: a promotion whose storeIds is [] produced the discount row on an order placed in a specific store, while a promotion in the same list naming one other store could not reach it. So candidacy is gated by four independent things, none of which the promotions grid shows together: the isActive flag, the store list (empty = all), the start and expiration dates, and the conditions (the blade offers customer criteria - first time buyer, user group - then catalog conditions, then cart conditions). The grid's Active column is the isActive flag ALONE: a promotion can sit there as Active with an expiration date years in the past and a store list that excludes the store you are testing, and nothing on that screen says so. Priority is a field on the promotion and is not what breaks a tie between two cart-subtotal rewards. One more coordinate worth knowing before you go looking for it in the store: Marketing.Promotion.CombinePolicy, the setting that decides whether rewards stack, is PLATFORM-WIDE on this deployment - GET /api/platform/settings/Marketing.Promotion.CombinePolicy returns objectId null, objectType null, groupName Marketing|General, and it is absent from the store's own settings collection - so changing it changes every store at once.

**Anchor corrected.** `GET /api/platform/settings/Marketing.Promotion.CombinePolicy` → `GET /api/platform/settings/{name}` — Named with the setting substituted into the path; the projected coordinate is the templated route.
