The sort argument is never validated, and every malformed form still returns HTTP 200 with no GraphQL error and a plausibly ordered page -- so a sort assertion that contains a typo passes vacuously. Three forms were observed on B2B-store, USD/en-US, 4550 products, anonymous. (1) An UNKNOWN FIELD is ignored: sort:"nosuchfield:asc" answers 200 with no errors array. It does not fall back to the default order (sort:"" starts Canon Imageclass / Xerox WorkCentre / Epson Expression) and it is not name ascending (sort:"name:asc" starts 0.6L Electric Drip Coffee Maker / 1 Book Retro Spiral Coil). It returns its own stable alphabetical-LOOKING order beginning at B -- Bestoss Nvme M2 Ssd, Bicycle Phone Holder, Bicycle Scooter, Big brand super high-definition, Bike Phone Holder -- which is the trap: the page looks sorted. (2) There is ONE fallback, not a per-field one: two different unknown fields, sort:"nosuchfield:asc" and sort:"alsobogus:desc", return byte-identical first-20 lists, and the DIRECTION is ignored along with the field -- nosuchfield:asc, nosuchfield:desc and a bare NOSUCH are all the same order. (3) On a VALID field an invalid direction silently means ascending: sort:"price:sideways" and a bare sort:"price" both return exactly sort:"price:asc" (GPS Smart Air Tag 2, GPS Tracker 2, Grand Theft Auto 3). The consequence for a test: never assert that a sorted query SUCCEEDED, because it always does. Assert the ordering of the returned values themselves, and pin the sort field name against the schema -- a renamed or misspelled field degrades into a different sorted-looking list rather than an error, and nothing in the response says so.
