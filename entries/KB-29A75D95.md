The storefront ships its colour presets bundled in the JavaScript as light and dark maps with the same keys (black-gold, default, mercury, purple-pink, watermelon, coffee, red), so a bundled preset requested as a file under /assets/presets/<name>.json returns 404 - only a name that is not bundled is fetched from there - and a 404 there is not evidence a theme is broken. The live preset is whatever the store's white-labeling record names (GET /api/white-labeling/store/{storeId} -> themePresetName, lower-cased with spaces as dashes); an unknown name falls back to the theme's default preset.

Dark mode (useDarkMode, vc-frontend #2200, in every theme from March 2026) is available whenever the active preset has a dark pair - every bundled preset has one - and is applied through an html.dark class. The header carries a "Theme" toggle (data-test-id dark-mode-toggle) for anonymous and signed-in shoppers, cycling auto -> dark -> light (auto -> light -> dark when the OS is dark), stored in localStorage vc-color-mode. In auto mode it follows the OS: emulating prefers-color-scheme dark sets html.dark and the dark tokens, and switching the emulation back removes it without a reload. Shoppers switch light/dark this way; they do not choose the preset. Observed live 2026-10-08 on theme 2.59.0 (Mercury) and 2.59.0-pr-2506 (Red).
