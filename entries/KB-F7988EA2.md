No -- the tree is stale. Cancel document updates the order blade's own header in place, but the operations-tree widget that draws the child PaymentIn and Shipment keeps the child objects it was given when the blade opened, and nothing re-reads them. So immediately after a successful cancel the header reads Cancelled while both children still read New, which looks exactly like a cascade that did not fire. It did: re-fetch and the payment is status Cancelled with isCancelled true, while the shipment genuinely stays New. Force the re-read by CLOSING the order blade and reopening it from the list -- an in-app hash navigation to the same orderId does not do it, because the blade is already open and is not rebuilt. The general rule: never read a child operation's state off the tree after acting on the parent; read it from the order API response.
