A Manager (non-administrator) user was given a role, a password-grant token was issued, then the role's permissions were changed via PUT /api/platform/security/roles (GET of the user confirmed the new permissions). Requests made with the ORIGINAL token kept returning 403 on endpoints the new permission should open (e.g. POST /api/taxes/search after adding tax:read), across nine successive role changes. The decoded token lists the permissions in its "permission" claim, and GET /api/platform/security/currentuser returns that same list. A token issued after the change got 200 immediately. So for bearer clients a role change takes effect on the next token (re-login or refresh), not on the next request. Observed 2026-10-13.
