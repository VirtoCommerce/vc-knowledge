On vcst_qa (RabbitMQ engine, no DistributedLock__KeyPrefix) the log shows 14 "Indexation skipped: the 'IndexationJob' lock is held by another run" errors (User admin, DocumentTypes Product) from 12:16Z to 13:27Z, starting 3 minutes after both platform pods restarted at 12:13Z, so a restart did not clear the lock. The setting VirtoCommerce.Search.IndexingJobs.CurrentJobId is null (no local holder recorded) and VirtoCommerce.Search.IndexingJobs.IndexationDate.{Product,Category,Member} are frozen at 2026-11-17T16:00Z although the IndexChangesJob recurring job (cron 0/59, enabled) last ran 13:00Z. vcptcore_regression (Hangfire engine, no prefix, IndexChangesJob every 8 min) is frozen the same way at 2026-11-17T16:08Z. vcptcore_qa1, the only one of these stands that sets DistributedLock__KeyPrefix, advanced its IndexationDate to 13:35Z today. vc-platform RedisDistributedLock uses the key "{KeyPrefix}:{resource}", or the bare resource name when no prefix is set, and DistributedLockOptions documents KeyPrefix as the way to isolate applications that share Redis. The stands set different Redis backplane channel names, which suggests they share one Redis instance; so stands without a prefix contend on one global "IndexationJob" key. Which stand or process holds the key was not identified (CurrentJobId was null on every stand checked).
