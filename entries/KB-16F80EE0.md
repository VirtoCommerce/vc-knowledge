2026-10-29 on vcst_qa, storefront origin. A throwaway Customer account (contact, storeId = an existing store that the run store B2B-store does not list in trustedGroups and that trusts nobody) took POST /connect/token grant_type=password with storeId=<its own store>: 200. With that Bearer, POST /graphql { passkeyCreationOptions } answered 200 with options whose rp.id and rp.name are the storefront host (the same host the run store's buyers get). Mutation createPasskey with a dummy credential "{}" answered INVALID_OPERATION from the resolver (not Forbidden/Unauthorized), i.e. the call is authorised and only the credential is wrong. The same account's password grant with storeId=B2B-store answered 400 user_cannot_login_in_store. So a contact of a foreign store can register a real passkey on the storefront host from a browser context (virtual authenticator) using its own-store token; nothing store-specific gates registration. Not observed: a real createPasskey ceremony, nor the passkey grant with storeId=B2B-store for such a key.
