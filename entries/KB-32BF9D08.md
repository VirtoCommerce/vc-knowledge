As admin on store Electronics (theme folder default), with the valid catalogHash: POST /api/site-builder/designer/save with themeFiles [{path:"custom-sections/<t>.json", content: a custom section whose template holds <script>, eTag from designer/theme-file}] answered 200 with warnings []. The Content API listing GET /api/content/themes/Electronics/search?folderUrl=custom-sections then showed /custom-sections/<t>.json-draft at the store's theme root, outside default/. The same content sent as default/custom-sections/<t>.json answered 400 ("<script> ... is not an element a custom section can hold"). The onclick and position: fixed rules behaved the same way: 200 on the un-prefixed path, 400 under default/ (3 of 3). A made-up folder behaves the same: agent-test/custom-sections/<t>.json -> 400, because the rules run on the path inside the theme, but agent-test/<t>.json -> 200. Even default/<t>.json (any file name the guard does not know) -> 200 unchecked. The stray file is read back only by GET designer/theme-file with that same path. It does not appear in theme/status drafts or newDrafts, in the MCP site-builder://stores/<store>/schemas resource, in the custom-section resource, in a publish_theme dry run or in designer/storefront, and the anonymous /cms-content URL answers 404. Traversal is refused: designer/theme-file with ../ or default/../../ answers 400 "must stay inside the store's content folder", and another store's name as the first segment resolves inside the same store's folder. The Vue designer and the MCP tools always prefix the theme name, so only a direct REST caller produces the stray path. The impact is storage pollution and a gap in theme confinement, not storefront script injection.
