Source (vc-platform): LocalStorageModuleCatalog validates every manifest module and adds module.Errors "Module dependency {declared} is incompatible with installed {version}" unless declaredDependency.Version.IsCompatibleWithBySemVer(installed.Version), which is Major == other.Major && Minor <= other.Minor (SemanticVersion.cs). Patch and prerelease are not compared, so 3.1037.0-alpha.284-<branch> is satisfied by 3.1038.0-pr-147-0d2f. A dependency that is not installed at all is not flagged by this check. The module's own platformVersion must also be <= the running platform and the same major. Live (vcptcore_dev, platform 3.1077.0-alpha): GET /api/platform/modules (admin token) returns each installed module with dependencies[] where version is an OBJECT {major, minor, patch, prerelease}, not a string, plus validationErrors[]; 90 modules, 0 validationErrors. Replaying the rule over those descriptors with VirtoCommerce.XCart swapped from 3.1039.0-alpha.289 to the PR build 3.1038.0-pr-147-0d2f flagged exactly one module: VirtoCommerce.SalesRep 3.1012.0-alpha.37 declares XCart 3.1039.0. The PR branch had last merged dev at 3.1038.0; dev was then bumped to 3.1040.0. So before pinning a PR build, compare its minor with the installed one and with every dependent's declared version; a stale PR branch needs a dev merge, not a deploy. Not observed as a live refusal: the pin was not deployed.
