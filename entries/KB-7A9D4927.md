---
No. A wishlist's sharing key is the id of its SharingSetting, and switching a shared list back to Private only suspends it: the key stays the same, and anyone who ever copied the link regains access the instant the owner shares the list again. There is no storefront control that issues a new key. Deleting the list IS a real revocation: after removeWishlist the old key resolves to null for an anonymous caller, the former reader and the owner. Treat a leaked list link as permanently leaked and delete the list rather than re-scoping it.

Observed live 2026-10-08 on theme 2.51.2 (XCart 3.1021.2) and on theme 2.59.0 (XCart 3.1039.0, Cart 3.1012.0): a list created Private and never shared already has a stable sharingSetting.id (the same on every read; the key the client sends with createWishlist is not the one stored); Anyone-with-link -> Private -> Anyone-with-link and Organization -> Private -> Organization keep that key; while Private, sharedWishlist(old key) returns null without errors and /shared-list/<key> shows the 404 page; on re-share the old link works again; after removeWishlist the key returns null.

On the pre-release builds of the sharing rework (x-cart 3.1037.0-pr-141 / 3.1038.0-pr-141 with cart 3.1011.0-pr-194, 2026-10-02 and 10-05) a never-shared Private list had no stored sharing row and returned a fresh id on every read; the released XCart 3.1039.0 keeps a stable id from creation again.
