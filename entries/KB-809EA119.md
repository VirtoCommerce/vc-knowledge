Live on vcptcore_qa1, fixture RETURNS_AUTH_PARTIAL_LINE: order line A is ordered=500, a prior return requested 240 of it and was decided PartiallyApproved with approved=200 (so 40 units released). The storefront's 'Select items to return' wizard showed this line's Returnable column as 300 (=500-200), not 40 -- i.e. returnable = ordered - approved, covering BOTH the 260 units never included in any return AND the 40 released-but-unapproved units, treated as one combined pool. After submitting a new return for 40 of those 300, the wizard's Returnable column read 260 (300-40), not 0. A follow-up attempt to return 41 more was accepted without any cap error (41 < 260). A test case (ORD-RET-014) that assumed the released 40 units WERE the entire returnable balance, expecting returnable to hit 0 after re-requesting exactly 40 and expecting a follow-up request of 41 to be refused as over-return, was built on a wrong premise for this fixture -- the platform's behaviour here is correct, not a bug.
