On vcst 2026-11-05 ~14:41Z, the Edge Playwright lane (persistent profile) had shown the stale entry twice that day (13:09Z and 14:30Z: remoteEntry.js 'HIT', last-modified 09:12:28, etag ...b50b8, hub chunks 404, /company/tasks stuck on 'Loading page…') while curl at the same minutes got the new object (last-modified 12:23:20, etag ...dab8). Clearing the browser's HTTP cache (CDP Network.clearBrowserCache) and re-requesting the same URL with the browser's own Accept-Encoding immediately returned last-modified 12:23:20 / etag W/"1dd6d207167dab8" (cf HIT). After signing in as a rep, every plugin chunk loaded 200 and /company/tasks rendered. So in these occurrences the old build was replayed from the browser's own cache: remoteEntry.js is requested without a version query and carries cache-control max-age=14400, so a browser that fetched it before a redeploy reuses it for up to 4 h. The replayed response still shows the stored cf-cache-status HIT / age headers, which makes it look like a CDN hit. That is also why the host's 'Reload page' does not recover it (KB-1BF50BB9): a reload reuses the cached entry. curl has no cache, so a command-line check passes. Recovery for a test lane: clear the browser cache (or use a profile with no cache) after every sales-rep redeploy. A CDN-held stale copy is a separate case (KB-4358B2EC, 2026-11-03, where a cache-busted origin request differed).
