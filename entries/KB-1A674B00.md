REST, throwaway customer on the B2B store with OTP sign-in on. Requested one code (POST /api/otp/request), sent 5 wrong codes to POST /connect/token grant_type=otp_email (400 invalid_code each), the 6th answered 400 user_is_temporary_locked_out with lockoutSecondsRemaining 898. The CORRECT code sent while locked: 400 user_is_temporary_locked_out, no token. An admin unlock right after (POST /api/platform/security/users/{id}/unlock: lockoutEnd cleared, accessFailedCount 0), then the same correct code: 200 with access_token, 14 s after the code was requested. So the lockout check refuses the attempt before the code is verified and the code is not consumed. Consequence: on a stand whose lockout lasts 900 s, waiting the lock out makes the code expire first (observed in regression case OTP-019: 400 invalid_code 15 min after the request) — the expiry, not consumption, is what refuses it.
