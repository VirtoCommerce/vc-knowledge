SalesRep 3.1013.0-pr-18 (VCST-5755) on a 2-replica stand, Cart TTL 60. The buyer's carts are not counted in the rep's cart statistics, so the number cannot show an eviction; a canary was used instead. The rep's Org-A cart-statistics key (period.to frozen in the future) was warmed with the Cart InvalidateOnChange flag on (tokened Cart:{Org-A}) on pod X and pod Y (4 = twin). The flag was set false (confirmed by settings GETs pinned to each pod) and the rep changed the Org-A cart line 3 -> 7: the key stayed 4 on X and Y while its cold twin read 8. The flag was set true (the flip alone does not evict a stale tokened entry), then the Org-A buyer (organization maintainer, not a rep) added a line to the buyer's own Org-A cart through pod X: the rep's key read 8 = twin 3/3 on pod Y (read first) and 3/3 on pod X, while the twin stayed 8 before and after the buyer's change. Positive control: a rep Org-A edit 7 -> 9 through X made the key 10 = twin on both pods. So the per-organization change token is shared by every actor in the organization: any cart change there evicts the rep's entry cluster-wide (a recompute with an unchanged result; performance-only, never a wrong value).
