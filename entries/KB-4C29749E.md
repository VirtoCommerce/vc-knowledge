On the stand, VirtoCommerce.Search.IndexingJobs.Enable=true with CronExpression "0/59 * * * *", so the recurring IndexChangesJob runs about twice an hour and replays changes from the VirtoCommerce.Search.IndexingJobs.IndexationDate.Product setting onwards. After a manual POST /api/search/indexes/index [{documentType:'Product', documentIds:[...]}] finished, that setting read 2026-09-28T14:30:02Z, the moment of the request. The Search module source explains this: the manual path (IndexAllDocumentsAsync) calls SetLastIndexationDateAsync(old, now). Products deleted at 13:16Z were still in the index at 14:10Z, after several scheduled runs, because a seeder's documentIds request at about 13:2xZ had already moved the date past the deletions. Consequences: with Catalog.Search.EventBasedIndexation.Enable=false, a catalog change reaches the index only at the next scheduled run (up to ~59 min away, not seconds), and never if anyone sends a manual index request in between, which seeders do routinely. A test that changes a product must send its own documentIds index request. A delete needs a startDate/endDate window over the deletion instead (see KB-31802239).
