Signed in as a sales rep in a fresh isolated browser context (Edge) and in a second lane (Chrome): /company/dashboard stayed on "Loading page…", My customers was missing from the hub sidebar, /company/customers gave 404, and the console showed "Failed to fetch dynamically imported module …/assets/dashboard-0lpkTCEg.js" plus 404s on link-my-customers-Dv6p461S.js, settings-*, utils-*, useBlockChrome-*, useSalesRepOrderStatistics-*. The browser received GET /modules/$(VirtoCommerce.SalesRep)/plugins/vc-frontend/remoteEntry.js and assets/virtualExposes-DXIYnlfF.js as cf-cache-status HIT, age 2144 s, cache-control max-age=14400, last-modified 16 Oct 2026 — an older plugin build — while mf-manifest.json was DYNAMIC with last-modified 22 Oct 2026. On the origin the 22 Oct build is consistent: remoteEntry.js → virtualExposes-EISDjs-f.js → dashboard-BhDxjIeQ.js / link-my-customers-BGPy2tAQ.js, all 200; the old build's chunks no longer exist there, so any old chunk whose CDN copy has expired 404s. curl of the same URLs (with or without gzip) got cf-cache-status BYPASS and the current build, so a command-line check does not show the problem. The literal "$(VirtoCommerce.SalesRep)" in the path is normal (plugin.json and the current assets resolve there). What follows: after redeploying a module that ships a storefront plugin, its pages can stay broken for browsers until the CDN copy of the unhashed remoteEntry.js expires (up to 4 h) or the cache is purged; check the browser's response headers (cf-cache-status, last-modified) rather than curl before calling it a product bug.
