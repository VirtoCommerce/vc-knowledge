POST /connect/token with grant_type=password for a CUSTOMER account (userType Customer) succeeds only with the form field storeId (camelCase) naming an existing store: no store, store_id, storeid, StoreId, an x-store-id header or an unknown store id all return 400 invalid_grant with code user_cannot_login_in_store ("Access denied. You cannot sign in to the current store"). The store check runs BEFORE the credential check: a wrong password with no or an unknown store also gets user_cannot_login_in_store, and only with a valid storeId does a wrong password get login_failed. The storefront origin and the platform host answer identically.

An Administrator-type user (isAdministrator true, no contact) is NOT refused: every variant - no store, storeId, store_id, an unknown store - returns 200 and a token with role __administrator; administrators can sign in to the storefront by design, with a restricted feature set. The storefront sign-in form itself never sends a non-email username: "admin" is rejected client-side with "Enter a valid email address, e.g. johndoe@gmail.com". Observed live 2026-10-08 on vcptcore_qa1 (platform 3.1077.0-pr-3123) and vcst_qa (platform 3.1076.0).
