2026-11-13, vcst_qa, client vc-mcp-onx (public, PKCE, implicit consent), resource registered as the onX /mcp URL. A token from the authorization-code flow with resource=<onX>/mcp carries aud=<onX>/mcp and works. A token from a plain password grant on the platform host (no resource; aud=resource_server, no client_id claim) ALSO passes initialize, tools/list and tools/call get-orders on onX /mcp. A token issued on the storefront host (iss = storefront) is refused 401 invalid_token "unexpected 'iss' claim value"; an unsigned token is refused 401 invalid_token. Source (VirtoCommerce/mcp-onx, branch virto, server/src/auth/token-verifier.ts): jwtVerify(token, jwks, { issuer }) with no audience option, by design comment 'the platform stays the authority'; the user's token is then forwarded to platform REST, which applies the user's permissions. So the RFC 8707 resource binding set up in the runbook (rsrc: permission, Authorization:Resources) does not restrict which tokens onX takes.
