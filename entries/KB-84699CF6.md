On vcst a disposable buyer requested OTP twice in a row (POST /api/otp/request, 200 succeeded=true each). The client took T0 = 13:58:21.386Z immediately before the second request; POST /api/notifications/journal keyword=<buyer email> sort createdDate:desc then returned two OtpSignInEmailNotification rows (status Sent) created 13:58:21.1355Z and 13:58:20.4657Z, i.e. the row of the second request carried a createdDate 0.25 s before T0 (server clock behind the client's by a fraction of a second; the HTTP Date header of both read the same second). A poll filtered by createdDate > T0 therefore never saw the row and timed out at 90 s (twice in a row), while a poll that treats as new any row whose id was not in the journal snapshot taken before the request found the code in 1-3 s. Identify the new message by its id (or snapshot the journal before the request), not by comparing createdDate to a client timestamp.
