Admin token, DefaultManualPaymentMethod payments set to Pending / Voided / Refunded through PUT /api/order/customerOrders (204). POST /api/order/payments/payment/capture {orderId,paymentId,amount:50,closeTransaction:true} on each returned HTTP 200 with body {"paymentStatus":null,"succeeded":false,"errorCode":"INVALID_REQUEST_ERROR","errorMessage":"Can't find payment in order"}. POST .../payment/refund {orderId,paymentId,amount:50,reasonCode:"Other"} on the Refunded payment returned HTTP 200 {"succeeded":false,"errorCode":"INVALID_REQUEST_ERROR","errorMessage":"Unable to process due to invalid payment status: Refunded"}. A subsequent GET of each order showed the payment status unchanged. An Authorized payment on an identically built order passed the lookup (different error, PAYMENT_FAILED, entity-save error on a synthetic order). So rejection is signalled in the body, not by the HTTP status; a client checking only 2xx would mistake it for success.
