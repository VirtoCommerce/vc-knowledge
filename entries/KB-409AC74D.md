Signed in on the storefront as a personal customer, a page fetch POST /graphql with no Authorization header (only the page's own cookies) answered Query.me with a NEW random id and userName "Anonymous", not the customer. Mutation.addItem sent the same way with that id created a cart with isAnonymous = true and customerName "Anonymous" (a guest cart). The storefront keeps its session token in localStorage key "auth" (access_token) and sends it as an Authorization: Bearer header; the same calls with that header answered the customer (me.userName = the e-mail, id = localStorage "user-id") and created a customer cart (isAnonymous = false). Consequence: an in-page GraphQL call meant to act as the signed-in user must send the bearer explicitly, or it silently acts as a guest — which made a mergeCart authorization case report a false failure (the "victim" was a guest cart, which mergeCart lets anyone merge by design).
