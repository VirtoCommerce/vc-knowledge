On vcst, a disposable Customer account (lockoutEnabled, store B2B-store, OtpSignIn.Enabled on) was locked by 5 wrong otp_email codes (5 x 400 invalid_grant/invalid_code; attempt 6 and the correct code: 400 user_is_temporary_locked_out, lockoutSecondsRemaining 898). After waiting 901 s: the ORIGINAL code (914 s old) answered 400 invalid_code; then POST /api/otp/request answered 200 succeeded=true, the new OtpSignInEmailNotification row was journaled in about 1.2 s, and POST /connect/token grant_type=otp_email with that fresh code answered 200 with an access_token. The users search then showed accessFailedCount 0 and a lockoutEnd already in the past. The sign-in log (POST /api/platform/security/sign-in-log/search, userName, startDate before the first request) held 9 signInType OTP rows: 5 InvalidCode (the wrong codes), 2 LockedOut (attempt 6 and the correct code sent while locked), 1 InvalidCode (the original code after the lock), 1 succeeded=true with no failureReason (the fresh code). The succeeded row was not in a read taken right after the grant and appeared by the next read, so the log is written asynchronously. So the lock needs no admin unlock: waiting it out and requesting a new code is enough.
