On platform 3.1079.0-alpha.13411, GET /api/platform/security/users/{userName} then PUT /api/platform/security/users with the same user object and passwordExpired=true answered 200 {succeeded:true, errors:[]}, but the re-read showed passwordExpired=false; the restore PUT with false was equally a no-op. The platform restores the protected user fields (PasswordExpired, LockoutEnabled, LockoutEnd, LastLoginDate, LastPasswordChangedDate, LastPasswordChangeRequestDate) from the database on this endpoint unless the AllowUpdateProtectedUserFields authorization option is enabled, so a test that flips passwordExpired this way runs against a NOT-expired account. The reset-password endpoint with forcePasswordChangeOnNextSignIn is the other path that sets the flag, but it rewrites the credential and terminates the user's sessions.
