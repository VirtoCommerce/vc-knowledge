Observed on Return module 3.1003 (PR builds 3.1003.0-pr-27-51fc among them) with Notifications 3.1014 and PushMessages 3.1006 (3.1006.0-pr-28-2027). Each status change to Requested, Approved, PartiallyApproved, Rejected or Cancelled enqueues two Hangfire jobs (SendNotificationsAsync, SendPushMessagesAsync), producing exactly one email and one push. The email is stored in POST /api/notifications/journal with tenantIdentity {id: returnId, type: Return} (status Error with SentNotificationException when SMTP rejects it, which still proves it was raised); the push is a PushMessage in POST /api/push-message/search with topic = return number, shortMessage = the rendered email subject, memberIds = [the buyer contact id], status Sent. xAPI submitReturn (Draft -> Requested) raises ReturnRegisteredEmailNotification with push text 'Return <number> received'; decisions raise ReturnPartiallyApprovedEmailNotification / ReturnRejectedEmailNotification with push texts 'partly approved' / 'declined'. Draft create/edit/cancel, a return created as New, and PUTs that keep the status send nothing. The decision call returns 200 even though SMTP fails. In one of about ten decisions (a fr-FR return) both jobs finished Succeeded in ~15 ms and produced no email and no push; requeueing the same jobs from the Hangfire dashboard with the same argument produced both, so the first run skipped the send for a reason that had gone by the time of the retry. Language: messages are stored under Return.languageCode (culture at createReturn), null falls back to the store default; with only the shipped template the text is English for every language. Writing Return.SendNotifications=false through POST /api/platform/settings/v2/tenant/Store/{id}/values did not reach the store read by the handler within 10 minutes (GET /api/stores still showed no value, and a submit still sent the email); an empty string for that boolean returns 500 and null does not clear the value.
