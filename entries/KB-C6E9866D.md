Storefront B2B buyer, lockout enabled, accessFailedCount 0. Operator with only platform:security:loginOnBehalf impersonated the buyer (storefront /account/impersonate/{userId}, grant_type=impersonate, token carries vc_operator_user_id). In that session the storefront /account/change-password form with a wrong current password sent Mutation.changePassword -> 200 data.changePassword succeeded=false errors PasswordMismatch 'Incorrect password.', UI 'You entered the wrong current password, please try again or call support'; the buyer's accessFailedCount (admin users/search) went 0 -> 1. The same mutation sent with the impersonated bearer from a script also returned PasswordMismatch. So the mutation is not refused for an impersonated token and each failure feeds the target's lockout counter (the handler calls AccessFailedAsync on failure). REST POST currentuser/changepassword answers 403 to the same token (Customer-type barrier). A successful own password grant reset the counter to 0.
