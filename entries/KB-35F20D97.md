No. addCoupon has no failure path for a bad code: it answers HTTP 200 with no errors array and an empty CartType.validationErrors whatever you send it, and it APPENDS the code to cart.coupons and persists it. The only thing that says it did not work is CouponType.isAppliedSuccessfully=false on that entry, plus the absence of a matching row in cart.discounts. So a cart can permanently carry codes that bought nothing, and the platform REST projection of that cart cannot even tell you that -- there coupons is a bare array of strings, so a dead code and a working one look identical. isAppliedSuccessfully is COMPUTED PER READ, not stored: change the promotion so it stops matching the cart and the very same stored code flips true to false on the next read with no cart mutation in between. Adding the same working code twice is idempotent -- one entry, one discount row, no doubling. The only pre-check is Query.validateCoupon, which returns a BARE Boolean with no reason attached, and its false collapses at least four different situations into one bit: no such code, right code in the wrong case (matching is case-sensitive), right code with surrounding whitespace (it is not trimmed), and a live code on an active promotion whose cart condition this cart does not meet. A caller that wants to tell a shopper WHY has nothing in the contract to build the sentence from.
