No. addCoupon has no failure path for a bad code: it answers HTTP 200 with no errors array and an empty CartType.validationErrors whatever you send it, and it APPENDS the code to cart.coupons and persists it. The only thing that says it did not work is CouponType.isAppliedSuccessfully=false on that entry, plus the absence of a matching row in cart.discounts. So a cart can permanently carry codes that bought nothing, and the platform REST projection of that cart cannot even tell you that -- there coupons is a bare array of strings (beside a singular coupon field), so a dead code and a working one look identical. isAppliedSuccessfully is COMPUTED PER READ, not stored (observed 2026-09: change the promotion so it stops matching and the stored code flips to false on the next read). Adding the same working code twice is idempotent -- one entry, one discount row; the same code in another case does not add a second entry either. The only pre-check is Query.validateCoupon, a BARE Boolean with no reason; its false collapses several situations into one bit: no such code, the code with surrounding whitespace (it is not trimmed: " QA " and "QA " are false, and addCoupon appends " QA " as a separate, unapplied entry), an inactive promotion, and a live code whose cart condition this cart does not meet. Matching is case-INSENSITIVE: validateCoupon is true for the code in any case. Observed live 2026-10-08 on vcst_qa (Marketing 3.1009.0, MarketingExperienceApi 3.1004.0); case and whitespace behave the same for cart dedup on vcptcore_stable (Marketing 3.1005.0). The order of cart.coupons can change between successive mutation responses on the same cart.
