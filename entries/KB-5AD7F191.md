On VirtoCommerce.MCP 3.1000.0-pr-1-df74 (platform 3.1096.0), POST {BACK_URL}/admin/mcp with a JSON-RPC initialize and no Authorization header returns 401 with `WWW-Authenticate: Bearer realm="{BACK_URL}", resource_metadata="{BACK_URL}/.well-known/oauth-protected-resource/admin/mcp", scope="openid profile offline_access"`. GET of that metadata returns 200 JSON: resource = {BACK_URL}/admin/mcp, authorization_servers = [{BACK_URL}/], scopes_supported openid/profile/offline_access, bearer_methods_supported [header], resource_name "Virto Commerce Back Office". On the storefront host, {FRONT_URL}/.well-known/oauth-protected-resource/ucp/mcp names the storefront as resource origin and authorization server (resource_name "Virto Commerce UCP"), while /ucp/mcp itself serves initialize and tools/list anonymously (25 tools, stateless: no Mcp-Session-Id). An authorization-code + PKCE flow started from that metadata (client claude-admin-qa, resource={BACK_URL}/admin/mcp) lands on the platform's own login page (/?ReturnUrl=/connect/authorize…), then the consent page, and the code exchange returns a token whose aud is exactly {BACK_URL}/admin/mcp and client_id claude-admin-qa.
