With a token from grant_type=impersonate (operator holds loginOnBehalf; token carries vc_operator_user_id), xAPI passkeyCreationOptions, createPasskey, renameSignInKey and deleteSignInKey each returned GraphQL error 'Access denied.' code Forbidden, before any key lookup (bogus ids used); the target's own password token gets passkeyCreationOptions data. Query signInMethods is allowed and lists the target's keys. xAPI changePassword with a wrong old password returned succeeded=false PasswordMismatch, i.e. it reached the password check rather than an impersonation refusal. REST currentuser/changepassword, currentuser/sign-in-methods DELETE, /api/passkeys and /api/passkeys/creation-options return 403 to the impersonated token, but also 403 to the Customer's own token, so that 403 is the Customer-type barrier, not an impersonation guard. On the storefront /account/security during impersonation only the 'Security' heading renders: the Passkeys section is absent, with no explanation; the sidebar still links Security and Change password.
