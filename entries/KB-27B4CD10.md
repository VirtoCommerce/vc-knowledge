The Active column on the storefront's company members roster is derived from TWO inputs, and the
security account's state is not one of them. The page renders
`isLockedInOrganization ? Locked : contact.status` (client-app/pages/company/members.vue) and the
roster query selects both fields (getOrganizationContactsQuery). So exactly ONE lock axis reaches
the column: the per-organization membership lock
(POST /api/customer/organization-memberships/{id}/lock), which paints the row with a red "Blocked"
badge and flips back to Active on unlock. Block user and Unblock user on the roster round-trip with Admin: blocking a member there flips the Admin account's 'Locked state' to Locked and unblocking flips it back to Unlocked, so the surfaces agree when the storefront is the one writing it.

Two other axes never reach it. Locking the security account itself
(POST /api/platform/security/users/{id}/lock, lockoutEnd 9999-12-31) leaves the row green and
Active. So does setting the contact-level Status to Locked in Admin. Admin carries two independent
per-account fields the roster does not project: Status (observed values Approved, Locked,
PendingApproval) and a derived Locked state (Unlocked/Locked). A contact whose platform account is
Locked, and a contact still PendingApproval because the invitation was never completed, both keep
contact status Approved and therefore both render as Active with the green tick. There is no second indicator anywhere on the page, so a maintainer is shown a colleague as able to sign in when the platform will refuse them.

So the column answers "is this member blocked in THIS organization?", never "can this colleague sign
in?". To learn whether a colleague can actually sign in, read the account blade under
Security > Users > account > Locked state, never the storefront roster.
