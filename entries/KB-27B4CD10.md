The Active column on the storefront company members roster never reflects the SECURITY ACCOUNT's state - locking a member's platform account (POST /api/platform/security/users/{id}/lock, lockoutEnd 9999-12-31) leaves the row Active on every theme, because the roster query selects securityAccounts { id email roles } and no lockout field. So the column never answers "can this colleague sign in?": read the account under Security > Users > account > Locked state for that.

What the column does reflect depends on the theme:
- theme <= 2.51.0: the query selects contact status only, and the badge is contact.status. A contact-level status of Locked shows Blocked; there is no per-organization lock field at all.
- theme 2.51.2 - 2.54: the query also selects isLockedInOrganization, but only the row's menu uses it (Block user / Unblock user); the badge is still contact.status. A membership lock (POST /api/customer/organization-memberships/{id}/lock) leaves the badge unchanged and only flips the menu to Unblock user; a contact-level Locked shows Blocked. Observed live 2026-10-08 on theme 2.51.2.
- theme >= 2.55 (vc-frontend #2399): the badge is isLockedInOrganization ? Blocked : (statusInOrganization ?? status). The membership lock shows a red Blocked badge and flips back on unlock; a contact-level status of Locked no longer reaches the badge and the row stays Active. Observed live 2026-10-08 on theme 2.59.0.

What Block user / Unblock user on the roster write also depends on the build: up to ProfileExperienceApi 3.1007 they set the contact status and lock the security account, so Admin's Locked state round-trips with the roster; from 3.1008 they lock only the organization membership and the account is untouched (see KB-DA14E8B7).

Note on this entry's history: its original headline (no lock field reaches the column) was right on the build it was written on (theme 2.39.0); the 2026-09-20 revision that called it "wrong when written" compared it with a newer theme.
