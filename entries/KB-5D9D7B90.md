With the storefront store at defaults (scannerEnabled=true, fields=[]) and a second, dedicated store saved as exact mode (fields gtin, code, manufacturerPartNumber, one property field) through PUT /api/catalog/barcode-search/store/{id}, an anonymous visit to /search?barcode=<a product's GTIN> stayed on the search page with 'No products found for barcode' (full-text path). After the SAME exact-mode settings were saved on the storefront's own store and the storefront was reloaded, the same URL redirected to the product page. So the settings that drive the storefront are those of the store it serves; a store with no storefront URL (reached only by store id over REST/xAPI) cannot influence it. Consequence for tests: a browser journey must write the storefront store's settings; a dedicated store's settings are only observable through REST/xAPI. With scannerEnabled=false the scan button was absent in the desktop header and in the mobile search overlay (390 px) while the bookmarked URL still resolved to the product page.
