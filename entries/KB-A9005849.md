On the Catalog Personalization PR build that added authorization (3.1007.0-pr-93), the read actions (GET /api/personalization/taggeditem/{id}, GET /api/personalization/taggeditem/{id}/tags/count, POST /api/personalization/search) pass for any principal holding catalog:read, catalog:products:read or catalog:categories:read, assigned globally or scoped to ANY catalog. The scope is not evaluated: a user whose catalog:read is scoped to catalog A receives tagged items from all catalogs in POST /api/personalization/search. Observed live with a non-admin user and a fresh token. The module developer confirmed this is intended: any catalog read access is enough, per-catalog filtering would require moving the whole logic. Write actions (PUT taggeditem, outlines synchronize/cancel) require personalization:update.
