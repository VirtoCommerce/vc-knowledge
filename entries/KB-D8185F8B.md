Build 2232d606, non-admin with platform:security:update. 10 concurrent POSTs of one fresh 40-char value for one user, 10 mixed POST/PUT(new) across two users, 5 PUT-existing + 5 POST, and 8 PUTs moving two existing keys to one value: every batch had no 500, exactly one row holding the value, the rest 400 "This API key cannot be used. Send an empty value to have the platform generate one." Re-saving a key with the value it already holds returns 200 (and echoes the value); the same value on another of my keys, a new key for me, or a new/existing key of another user all return the same 400 text with the same latency (median 194–201 ms, same as a length 400 at 190 ms), so the refusal does not say whose key it is, but 400 vs 200 still tells a security:update holder that a value is live. A user with only order permissions gets 403, anonymous 401. DELETE of the holding key, then POST of the same value for another user, returns 200 and the value authenticates as the new owner; the old row's value got 401 right after the delete. A POST body that is a JSON array returns a bare 400.
