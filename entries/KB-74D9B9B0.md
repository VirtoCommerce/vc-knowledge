POST /api/platform/localizable-settings/{name}/dictionary-items (the Admin dictionary editor's save, LocalizableSettingService.SaveAsync) first re-saves the alias list, then groups the STORED PlatformLocalizedItem rows by Alias case-insensitively and builds a per-LanguageCode dictionary for each group. If two stored rows for the same setting and language have aliases that differ only in case (e.g. 'new' and 'New'), every save of that setting throws ArgumentException and returns 500 'An item with the same key has already been added. Key: en-US', whatever is posted, including the unchanged GET output. Nothing is written or deleted; the translations stay as they were. GET /api/platform/localizable-settings cannot show the offending row, because GetItems matches aliases to allowed values case-sensitively, so the Admin UI cannot fix it either. No REST route lists raw rows. The only index is IX_PlatformLocalizedItem_Name_Alias, which is non-unique and excludes LanguageCode, so the schema does not prevent such rows. Observed on Order.Status on platform 3.1072.0 (4/4 failures); the same unchanged save returned 204 on 3.1074.0 and 3.1075.0, which run identical code. Recovery is a DB cleanup of the stray row. Platform export/import is not a documented fix.
