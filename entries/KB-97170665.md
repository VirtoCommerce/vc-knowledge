Admin's "Lock in organization" and the storefront's own "Block user" action both hit the membership lock axis: POST /api/customer/organization-memberships/{id}/lock, xAPI mutation lockOrganizationContact. Measured on vcst-qa 2026-09-19 against org AGENT-TEST-Org-TechFlow-20260310 (96f109a7-9010-4691-b6a1-bef25cca3d04) with fixture "Blocked User" (membership 9bde8cca-0a1f-4962-86e4-b3ba69e2023b), calling as agent-test-impersonator@virtoworks.com on an org-scoped /connect/token. Locked state: REST membership isLocked=true, lockoutEnd=null, status="Approved"; xAPI organization.contacts.items returns status="Approved", statusInOrganization="Approved", isLockedInOrganization=true; the storefront /company/members row renders the Active column as a red "Blocked" badge (icon alt text "Blocked") and the row action menu offers Edit role / Unblock user / Delete / Login on behalf. Proven causal by a round trip: POST /unlock gives isLockedInOrganization=false and the badge flips to "Active"; POST /lock puts both back. So the ONLY API field carrying the block is isLockedInOrganization; anything asserting on status or statusInOrganization reads "Approved" for a blocked member. Badge rule observed across the full 15-row roster: lock wins, otherwise statusInOrganization maps Approved to Active, Invited to Invited, Locked to Blocked, and everything else (Rejected, Deleted) to Inactive. Storefront build 2.58.0-pr-2467-1f40-1f40b001, a PR build rather than a release; the vc-frontend pr-2407 checkout of 2026-07-31 renders the badge from contact.status alone and would show a locked member as Active, so this is pinned to the deployed build.
