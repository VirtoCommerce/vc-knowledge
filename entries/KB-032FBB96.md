What you are allowed. sharingSetting.access and sharingSetting.isOwner are evaluated against the calling principal, not stored on the list, so the same list returns different values to different callers on the same request shape. One list observed both ways within minutes: to its owner, access Write and isOwner true; to an anonymous caller holding its key, access Read and isOwner false - same sharingSetting.id in both responses. Read it as an answer about this caller and never cache it across principals. Note also that the read grant it reports is wider than the write grant the storefront exposes: the /shared-list/<key> page it backs renders with no edit, no delete and no add-to-cart control for ANY holder, the owner included, so Write on that field does not correspond to a writable screen.
