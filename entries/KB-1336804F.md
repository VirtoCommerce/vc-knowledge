On PageBuilderModule 3.1034.0-pr-167-0ed1 (the build of the open concurrency-token PR), as administrator over HTTP with two independent token grants: GET /api/page-builder-pages/grouped/{groupId}/content?draft=true&includeVersion=true returns { content, eTag } where eTag is a strong quoted hash. POST …/content with the document body and that token in If-Match succeeds (204 plus an ETag header, or 200 { eTag } with ?includeVersion=true on the POST). Two sessions that read the same version and then both save: the first gets success, the second gets 412 'The page content version does not match the current version.' and the first author's content is kept; a fresh read plus retry then succeeds. No If-Match gives 428; a weak token (W/"…"), '*' or a comma-separated list gives 400. Six simultaneous writers on one version gave exactly one success and five 412, and the stored content was exactly the winner's. POST …/content-json takes the token in the body eTag (or If-Match); header and body that disagree give 400. TRAP: on this stand the plain ETag RESPONSE HEADER of the GET arrives as a weak W/"…" validator whatever Accept-Encoding is sent (the edge proxy rewrites it), while the body eTag stays strong with the same hash. A client that echoes the header into If-Match therefore gets 400 on every save; the README's documented proxy-safe route is includeVersion=true on both GET and POST, which is also what the Designer uses. The pre-fix build 3.1032.0 on another QA stand accepts both saves with 204 and keeps only the last writer's content.
