On a platform build with SHA-256-hashed user API keys (PR build of vc-platform 3.1105), a key was warmed with repeated calls, then regenerated: the old key answered 401 on a protected endpoint (POST /api/order/customerOrders/search) from the first call after the regenerate response, in sequential and 10-way parallel bursts, header and query alike; requests racing the regenerate call itself returned 200 until it completed. PUT users/apikeys with isActive=false gave 401 at once; PUT isActive=true restored the SAME key at once; DELETE gave 401 at once. Role removal from the owner turned the key's 200 into 403 on the next call. A non-administrator holding platform:security:access/read/update/delete got 403 for PUT (deactivate), POST (create for the admin), regenerate and DELETE on an administrator's key; a DELETE batch mixing one of its own keys with the admin's key was rejected whole (403) and its own key survived. Moving a key between users (PUT/POST with another user's id or key id) answers 400 "An API key cannot be moved to another user." Note: GET /api/platform/security/currentuser answers 200 {} for an anonymous or wrong-key request, so it cannot be used as the auth oracle — use a permission-protected endpoint.
