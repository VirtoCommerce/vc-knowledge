Yes, and exactly one field says so: DiscountType.coupon. Held the same promotion, the same RewardCartGetOfRelSubtotal, the same description and the same promotionId, and only added or removed its coupon: while the promotion required a coupon the cart's discount row carried coupon="<the code>", and the moment the promotion's last coupon was deleted -- which is also what flips the REST promotion's hasCoupons to false -- the identical reward came back on the identical cart with coupon=null. Nothing else moves: description, amount, promotionId are byte-identical across the pair, so a caller that does not select 'coupon' cannot tell the two apart at all. The field means 'this reward was unlocked by this code', not 'this cart has coupons on it' -- in the automatic reading the cart still carried a coupon entry (a dead one) while the discount's coupon was null. Note the asymmetry with the storefront page, which selects DiscountType.coupon and then never renders it: the discount line shows description and amount only, so the shopper is never shown which of their codes bought which reduction.
