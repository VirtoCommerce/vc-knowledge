On x-cart 3.1037.0-pr-141 / cart 3.1011.0-pr-194, the createWishlist/changeWishlist response lists targets in the order the ids were added, but every later wishlist(listId) read (and later saves) returns them in a different, stable storage order. The owner's deprecated sharingSetting.sharedWithId is the FIRST target of whichever order that response uses, so it differs between the create response and later reads. Legacy sharedWithId writes compare against the first target only: re-sending the first target is a no-op, sending any other id on a multi-target list (including the second target, or the id the create response reported) is refused INVALID_OPERATION and writes nothing. Without scope, a legacy sharedWithId is ignored silently.
