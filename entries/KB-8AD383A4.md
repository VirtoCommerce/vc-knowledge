On PageBuilderModule 3.1036.0-pr-178 (which makes POST/PUT /api/page-builder-pages/grouped and create-group-page return 400 for permalinks containing whitespace, ? # & \, //, ./.. segments), a hand-built backup zip (Manifest.json + PlatformEntries.json {} + VirtoCommerce.PageBuilderModule.json = {PageBuilderSharedComponents:[], PageBuilderPages:[{groupId,name,permalink,storeId,cultureName,visibility,variants:[{pageId,status,content}]}]}) uploaded to POST /api/assets?folderUrl=backups and restored via GET /api/platform/export/manifest/load?fileUrl=backups/<zip> then POST /api/platform/import {fileUrl, exportManifest, modules:["VirtoCommerce.PageBuilderModule"]} completed with 0 errors, and GET /api/page-builder-pages/grouped/{id} returned permalinks such as "/x legacy-s8?x", "/x legacy-s10#y", "/x-S7&x" byte-for-byte; the pages are found by POST /api/page-builder-pages/search immediately. Import upserts by the supplied groupId and saves variant content only when pageId is given. The validation lives only in the controller, so restore is a path for legacy-invalid data. Separately: POST /api/platform/export must carry exportManifest (the manifest/new body) alongside modules[] — without it the backup job finishes with a bare NullReferenceException.
