On vcst a TechFlow-org membership (Approved, membership-locked) carried roles [Organization employee]. GET /api/customer/organization-memberships/{id}, then PUT the same body with roles = [existing item, {roleId: "purchasing-agent", roleName: "Purchasing agent"}] returned success; the read-back membership listed both roles (each as {membershipId, roleId, roleName, id}), with isLocked, status and lockoutEnd unchanged, and the user's security-account roles stayed empty. Querying organization(id).contacts { rolesInOrganization { id name } securityAccounts { roles { id name } } } as the organization maintainer returned rolesInOrganization = [Purchasing agent, Organization employee] for that contact (newly added role first), with no account roles. So a second organization role belongs on the membership's roles array, not on the security account. Also seen in the same run: a contact with an Approved membership in the org but an empty contact.organizations did NOT appear in organization.contacts at all, so it is the wrong member to change if the change must show on /company/members. Side observation: the stock roles Organization employee and Purchasing agent carried the identical permission set (storefront:organization:view, storefront:user:view), Sales Representative only sales-rep:access.
