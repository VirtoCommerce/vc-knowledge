On a 2-replica stand with Redis healthy (SalesRep 3.1013.0-pr-18-d367, platform 3.1076.0), TTL 60 min and the InvalidateOnChange flags on (defaults true for Cart/Order/CustomerCounts; TopSeller set true): each statistic was warmed on both pods (20 cookie-less + 2 pinned reads, one value), then a mutation, then 20 cookie-less reads starting 0-3 ms after the mutation response plus 3 pinned reads per pod. Every read (26 per key) equalled its cold twin (same query with period.to + n seconds) for: cart quantity up, line removed, rep checkout (cart drops to 0; order stats per org, all-orgs dashboard, customer counts, salesRepCustomers inline orderStatistics, and salesRepCustomers sorted by ytd-purchases and my-last-orders all fresh), admin PUT /api/order/customerOrders status New->Processing (status-filtered order stats and salesRepOrderFilterRules vocabulary fresh), and with TopSeller flag true salesRepTopSellers + salesRepTopSellerFilterRules. Directed form via INGRESSCOOKIE: warm a key on pod Y only, mutate through pod X, read Y within 1 ms - fresh in both directions. Post-hoc cookie mapping showed the first read after the mutation landed on the non-mutating pod and was already fresh. Dashboard (all served orgs) equalled the sum of per-org cards at every probe. With a flag false (Cart, or TopSeller at its default false) the warmed key stayed stale on every pod while its twin moved; entries cached while a flag was off stayed stale after flipping it on, and setting TTL 0 did not flush an existing entry - both as the developer documented.
