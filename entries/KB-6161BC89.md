POST /api/catalog/products/configurations/search is where configurability is read, but an empty criteria body counts configurations regardless of isActive, so its totalCount is not the number of configurable products on the deployment. Creating one configuration and then deactivating it (POST with isActive false) leaves the empty-body count one higher than {isActive:true}; {isActive:false} returns the deactivated row. There is no delete route (DELETE on /configurations/{id} and /configurations?ids= answer 405), so a deactivated row stays in the count for as long as its product exists. Deleting the PRODUCT does take the row out of every search - empty body, {isActive:false} and {productId} - although GET /api/catalog/products/configurations/{id} still returned it minutes later. Repeating identical criteria right after a write can return a cached total; vary the criteria to read a fresh one. Use {isActive:true} for the count of products a buyer can actually configure. Observed live 2026-10-08 on vcst_qa, vcptcore_qa1 and vcptcore_stable.
