Build: Return 3.1005.0-pr-28-fb4f, theme 2.60.0-pr-2523-466f, 2026-10-09.

Steps:
1. Created an order through admin REST POST /api/order/customerOrders, then completed it with a delivered shipment. Its customerId was the buyer's user id in UPPERCASE, as an integration that writes GUIDs upper-case would send it. The buyer's platform user id is lower case.
2. As the buyer, with an organization-scoped token, called Query.returnableItems(orderId). It accepted the order: isReturnable=true, returnableQuantity=5.
3. Mutation.createReturn returned a Draft whose customerId was the UPPERCASE id, copied from the order rather than from the signed-in user.
4. submitReturn moved it to Requested. GET /api/return/{id} shows customerId in UPPERCASE, with createdBy and modifiedBy both the buyer. No admin touched the return itself.

Server result: return(id) for the buyer gives availableActions cancel isAvailable=true, and the buyer's returns list includes the return.

Storefront result: opening /account/returns/{id} from My returns, signed in as that buyer, shows the colleague variant: a "Requested by <buyer's own name>" row and no "Cancel return" button.

What follows: the letter-case mismatch reaches the storefront without any back-office edit of the return. An order whose customerId was written in another case (by an integration or an import) is enough. Every return the buyer files on that order loses its Cancel button on the details page.
