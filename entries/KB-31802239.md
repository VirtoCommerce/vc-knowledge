On a stand with Catalog.Search.EventBasedIndexation.Enable=false, deleting products via DELETE /api/catalog/products (including products deleted and recreated with new ids) left all their Product index documents in place (ElasticSearch8), still there 50+ minutes later: xAPI Query.products hits and totalCount exclude them, but admin POST /api/catalog/search/products counted them in totalCount while items held only live products (24 for 12 returned items), and xAPI term facets counted them too (a GTIN held by 3 live products showed bucket 6; a bucket reported 2 per product). A facet on createddate shows the old and new docs apart. It does not reproduce on untouched catalog products. An incremental edit was also not picked up by the scheduled indexing job within 10 minutes; a targeted POST /api/search/indexes/index for that document id fixed that one document. POST /api/search/indexes/index with [{documentType:'Product', documentIds:[deleted ids]}] cannot fix the deleted ones: the Search module treats explicit ids as Modified changes, a missing product builds no document, and nothing is removed. POST /api/search/indexes/index with [{documentType:'Product', startDate, endDate}] and NO documentIds replays the catalog change feed for that window, and the Deleted CatalogProduct operation-log entries in it become index removals: 14 ghost documents (12 products + 2 variations) disappeared within ~10 s for a 6-second window around their deletion time. The deletion times come from POST /api/platform/changelog/v2/search {objectType:'CatalogProduct', operationTypes:['Deleted'], objectIds:[...]}; the change log records deletions regardless of the event-indexation setting. Admin search with objectIds:[...] and searchInVariations:true returns totalCount = how many of those ids still have an index document, which is a cheap check that the purge worked. Keep the window narrow: everything else modified inside it is re-indexed as well.
