When a Customer account is genuinely password-expired, its xAPI buyer-scoped return calls - returns, organizationReturns, return(id), returnPolicy and the create/update/submit/cancel mutations - answer HTTP 200 with data null and errors[].code PasswordExpired; returnStatuses and me still answer, because the check gates per buyer-scoped root field and reference data bypasses it. The state is read live per request (UserManagerCore.ValidateUserStateAsync FindByIdAsync, Xapi 3.1027.0: L82 throws PasswordExpired, L87 throws UserLocked), so a token minted before the expiry behaves the same as one minted after - token age is irrelevant. A password grant still issues a token to an expired account. With the account LOCKED instead (POST /api/platform/security/users/{id}/lock - by the account GUID; the userName is a silent no-op), the same calls answer errors[].code UserLocked and returnStatuses still answers; after unlock the token answers again. The flag only gets set the right way: POST /api/platform/security/users/{userName}/resetpassword {newPassword, forcePasswordChangeOnNextSignIn:true} sets passwordExpired=true, while PUT /api/platform/security/users leaves it false (and cannot set lockoutEnd either). The original claim that an expired account 'still answers every return query and mutation' was observed on an account whose PUT never actually expired it (KB-87EC0A28). Observed live on a local current-manifest stack (Return 3.1005.0-pr-28-fb4f, 2026-10-13).
