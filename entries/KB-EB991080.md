A Product-type configuration section serves only those options whose product the storefront can resolve for that store, and it drops the rest SILENTLY -- no error, no null entry, no unavailable flag, just a shorter options array. Observed directly: a section built with three option products that the store's catalog links in but the storefront cannot resolve (Query.product by id returns null for them) came back from Query.productConfiguration as a section with options: [], while a sibling section in the same configuration whose options are ordinary storefront-visible products came back complete with listPrice, salePrice, extendedPrice = listPrice * quantity, currency and the whole nested Product. The dangerous case is that the filter does not respect isRequired: a section with isRequired true and every option unresolvable is served as a REQUIRED section with zero options, which no buyer can satisfy and nothing anywhere reports as broken. So the option products being present in the catalog, active, buyable and linked into the store's catalog is NOT sufficient -- they must also be storefront-resolvable, and a section that looks correct in Admin (which reads the configuration through the catalog API and shows every option) can be empty on the storefront. Diagnose it by asking the storefront for each option product by id on its own: whichever returns null is the one being dropped.
