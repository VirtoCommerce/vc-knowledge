Admin token, one rep's tasks (7 typed "Call", 1 typed "CALL"), POST /api/task-management/search {responsibleIds:[rep], type, take, skip:0}. With otherwise identical criteria, all letter-case variants return the result of the variant searched first: "CALL" first -> "CALL", "Call" and "call" each return only the "CALL" task; "call" first -> all three return 0; "Call" first -> all three return the 7 "Call" tasks. 4/4 rounds, each on a fresh key family (different take). Keyword behaves the same ("x9" first -> "X9" 0 rows; "X9" first -> "x9" 1 row). The database answer is case-sensitive (WorkTask.Type and Name use the database default collation, not the case_insensitive collation other modules apply on PostgreSQL), so only the first variant is computed; the others are served from the cache. Reachable from the Admin UI alone: Tasks app (/apps/tasks) > All tasks, Search box "x9 lowercase" -> No results found, then "X9 lowercase" -> No results found (request {"take":20,"sort":"createdDate:DESC","skip":0,"keyword":"X9 lowercase"}), while the narrower "X9 lowercase call" -> 1 row, the task whose name contains "X9 lowercase". Source: platform SearchService caches the id list under CacheKey.With(type, "SearchAsync", criteria.GetCacheKey()); PlatformMemoryCache lower-cases every string key (CacheKey.Normalize, VCST-4012, since platform 3.915.0); TaskManagement WorkTaskSearchService filters with x.Type.Contains(criteria.Type) and Name/Description.Contains(keyword). The entry lives until a WorkTask save clears the search region or it slides out (Caching.CacheSlidingExpiration 15 min here). The Type filter in the Admin app offers only the dictionary spelling ("Call"), so through the UI the type variant is reached only via data written by API clients.
