Observed 2026-09-22 on vcst_qa (storefront Ver. 2.58.0-pr-2467-89a3-89a38239), store B2B-store, signed in as an org buyer (org AGENT-TEST-Org-AcmeCorp-20260310) with one physical item in the cart.

WHERE IT IS: payment selection is on the /cart page itself, in a "Payment details" section (alongside "Shipping details"), not on a separate /checkout/payment route. The control is a "Payment method*" dropdown.

WHAT IS OFFERED: six options, in this exact rendered order — "Bank card (Authorize.Net)", "Bank card (CyberSource)", "Bank card (Datatrans)", "Manual", "Pay with points", "Bank card (Skyflow)".

WHAT IS PRESELECTED: nothing. The control reads "Select a payment method" and no option carries a selected state. Place order is disabled with "Complete all required information to proceed." The list renders in full before any shipping address or delivery method is chosen, so it is not gated on shipping selection.

WHERE THE LIST COMES FROM: Query.cart.availablePaymentMethods returns exactly those six, in exactly the same order the dropdown renders them — the UI does no filtering or re-sorting of its own. Their codes/types/priorities: AuthorizeNetPaymentMethod (PreparedForm, priority 1), CyberSourcePaymentMethod (Standard, 0), DatatransPaymentMethod (Standard, 0), DefaultManualPaymentMethod (Unknown, 1), LoyaltyPaymentMethod (Unknown, 0), SkyflowPaymentMethod (PreparedForm, 0). Behind that, POST /api/payment/search returns 21 rows system-wide across all stores; B2B-store has exactly six rows, all isActive=true, with priorities that match the GraphQL priorities one-for-one. Six distinct method codes exist in the whole system, so B2B-store enables all of them.

ORDER IS NOT PRIORITY: with priorities 1,0,0,1,0,0 the rendered order is neither ascending nor descending by priority. It is alphabetical by method code (AuthorizeNet < CyberSource < Datatrans < DefaultManual < Loyalty < Skyflow). Note the platform developer guide states that a store's priority setting determines "the order in which the payment methods will be displayed at checkout" — that did not hold here.

LIMIT OF THIS OBSERVATION: every method row on this store is isActive=true, so this run does NOT demonstrate that setting isActive=false removes a method from the cart — only that the enabled set and the offered set coincide. The alphabetical-vs-priority conclusion also cannot distinguish alphabetical-by-code from registration order that happens to coincide with it. No order was placed and no store configuration was changed.
