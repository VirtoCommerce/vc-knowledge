On the storefront xAPI, a storefront user (personal contact, and separately an organization maintainer writing to the organization) sent one updateMemberAddresses command carrying 2, 3 or 8 new addresses with no ids. The response was HTTP 200 with an empty errors[], but a following currentCustomerAddresses / currentOrganizationAddresses read showed only the LAST address of the command added. With 3 new addresses the book grew by 1; with 2 it grew by 1 (one run by 0 to 1 more than expected); with 8 per organization it grew by 1. Sending one new address per call stored each one. Existing addresses absent from the command were kept, so the mutation behaves as an upsert by id, not a full-list replace. Two independent scenario runs saw it on the same build. No storefront UI path is known to send several new addresses in one call, so the effect is API-only.
