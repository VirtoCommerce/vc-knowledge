Inviting a member creates BOTH a contact and a security account immediately - the invitation is not a queued message, it is a provisioned account that cannot yet be used: the contact's status is Invited with an empty name, and the account carries lockoutEnd 9999-12-31, emailConfirmed false and no password. On the Admin account blade the same person shows Locked state = Locked and a Status field that is EMPTY (the account's own status is null), rendering as the 'Select ...' placeholder. So a pending invitee and a blocked member are both simply 'Locked' in Admin, and the field that could tell them apart is blank for the invitee. Do not read a Locked account as evidence that someone was blocked: check the contact's own status, where a pending invitation reads Invited.

Where the role chosen in the invite dialog lands depends on the build. Which build a stand runs decides this. G1 = ProfileExperienceApi (PEA) <= 3.1007, Customer 3.1000.x, theme <= 2.51.0 (vcptcore_stable until 2026-10-07). G2 = PEA 3.1008-3.1014, Customer 3.1010-3.1020, theme 2.51.2-2.54. G3 = PEA >= 3.1015, Customer >= 3.1021, theme >= 2.55. On G1 the invite assigns the role to the security account itself (InviteUserCommandHandler AddToRolesAsync). From Customer 3.1010 (G2, G3) an invitation into an organization puts the role on the ORGANIZATION MEMBERSHIP (rolesInOrganization) and the security account holds no roles at all - observed live on G2 and G3 on 2026-10-08. A security account with zero roles is therefore normal for an invitee on current builds, not a sign that something stripped them.
