The orders workspace takes an orderId in the hash (#!/workspace/orders?orderId=<id>) and it is not a reliable way to reach an order. Two separate failures. FIRST, it does not re-target: if an order blade is already open, navigating to the same route with a DIFFERENT orderId changes the URL and leaves the previous order on screen, so the address bar names one order while the blade shows another - the blade is not rebuilt, the same reason an in-app navigation does not refresh a stale operations tree. Close the blade and open the order from the grid. SECOND, on a COLD load the deep link wins the race against the UI localization bootstrap: the page throws dozens of TypeError: Cannot read properties of undefined (reading toLowerCase) out of the translate filter, and the blade comes up degraded - the title falls back to a generic 'Customer's order' instead of the customer's name, the Discount money field renders its input mask (##.##) instead of the value, the Created at field renders in a ja-JP pattern (y年M月d日 ah:mm:ss) and in the BROWSER's timezone rather than the profile's, and several widgets are missing. The totals widget and the operations tree still read correctly, which is what makes it dangerous: the screen looks usable and two of the fields an operator would quote are wrong or empty. Anything read off a deep-linked blade should be re-read after opening the order from the grid.

**Anchor corrected.** `GET /api/platform/localization?lang=en` → `GET /api/order/customerOrders/{id}` — The localization call was named with its query string and resolves to nothing; anchor instead on the call the order blade makes, which is what a contract change would reach.
