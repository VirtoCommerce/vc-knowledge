Introspecting the GraphQL type OrderConfigurationItemType on vcst-qa (VirtoCommerce.XOrder 3.1011.0, VirtoCommerce.Orders 3.1015.0, VirtoCommerce.Catalog 3.1044.0) returns 15 fields: id, sectionId, sectionName, name, productId, sku, imageUrl, quantity, type, customText, price, salePrice, extendedPrice, files, product. A Query.order(number:) selecting sectionId, sectionName, productId, sku, quantity, price{amount}, salePrice{amount}, extendedPrice{amount} and files{name url} executed cleanly (HTTP 200, no errors[]) and returned values identical to the same order read over REST via GET /api/order/customerOrders/{id} — same ids, same sectionIds, same productIds, same per-option prices. This directly contradicts KB-59E4B5FC, which observed on vcptcore_stable that this type exposes only id, name, type, customText and files and REFUSES productId, quantity, sectionId, sku, catalogId and categoryId with a validation error. The two deployments differ in module version, so the restriction should be read as version-bound, exactly as KB-F20CD11C already argues for the REST shape: on this build the GraphQL surface is NOT a lossy display projection, and a storefront order page CAN reconstruct the full configuration including which section each answer belonged to, without falling back to REST. The only two fields the GraphQL type lacks relative to the REST record are catalogId and categoryId. Practical consequence: a check asserting "section binding is unavailable over GraphQL" is wrong on this build and will pass vacuously — select sectionId and assert on it, rather than matching options by display name or by array position (array order genuinely does differ between the REST and GraphQL projections of the same order).
