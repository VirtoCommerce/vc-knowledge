On a vc-frontend 2.60 PR build (scope-slot loader, desktop 1920px), a MutationObserver+ResizeObserver timeline on .search-bar .vc-input__decorator during breadcrumb, sidebar, Back/Forward and /category/<id> redirect navigations shows: the loader first holds the previous slot width (or the 5rem/80px minimum when coming from no scope), then resizes to the new label's width ~2-3 ms before the chip replaces it. The input left edge therefore moves by the width difference (Printers<->Laser Printers: 31.36 px; empty->Printers via id redirect: 14.89 px; long labels: ~38 px), measured inside the loader phase; at the swap itself the delta is 0. Loader and chip are never present together, the slot is never empty during category->category, and the settled chip/placeholder name the new category. Painted, the input does not move inside the loader phase: on vcptcore (theme 2.60.0-pr-2522-6f90, 2026-10-13, 1920px, Chromium at 73-76 fps, 18 category-to-category transitions by sidebar and breadcrumb) every sequence of painted frames was old chip -> loader with the OLD label and OLD width for 280-1000 ms -> new chip. The loader's label mutation lands 1.4-5 ms before the chip remount, inside the same frame, so no frame ever shows the loader at the new width; the input left edge moves exactly once, at the loader->chip hand-over, by the label-width difference (7.38 and 106.31 px here). The width change measured above is a DOM state between two paints, not a visible one.
